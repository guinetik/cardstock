# #12 — Pin a lane so it stays in view while the rest of the board scrolls

## Ask

Split out of [[7]] on 2026-09-04, once that card's real question turned out to be
two questions wearing one coat.

[[7]] is Hap's complaint that the lane holding his work sat eighth from the left
behind a horizontal scroll bar, and took six turns of directions to reach. [[10]]
fixed the half that was a defect: every lane can now be dragged, so the lane that
matters can be moved left in one gesture.

That move is global, and deliberately so:

> Joao: *"scrum and kanban are collaborative stuff. if people cannot agree on lane
> order they shouldn't be messing with software engineering."*

Which leaves the half that is not a defect. A shared order is correct, and a person
can still want one particular lane in front of them at all times. That is not a
disagreement about the board — it is a personal view of it, and it gets its own
action:

> Joao: *"we could have two actions. move lane moves the lane on the board. pin
> lane pins it just for you in LS. your pin always in."*

## Status

**Claimed — in progress.**

## Rationale

Move and pin are two scopes, and keeping them apart is what makes both safe.

**Move** writes `lanes.position`, a shared column in the realtime publication. It
changes the board for everyone, immediately. [[10]] shipped it.

**Pin** changes nothing about the board. It is a rendering preference belonging to
one person: the pinned lane stays visible while the rest of the board scrolls under
it. Nothing reorders, so there is no reconciliation between one person's pin and
another's, and none between a pin and the shared order.

The board already has a precedent for per-viewer lane state — collapsed/min/max
lives in `members.prefs.laneViews`, keyed by board id. The pin deliberately does
**not** follow it into `members.prefs`: browser storage is cheaper, needs no
migration, and a pin is a per-screen convenience rather than something worth
carrying between devices. The cost is that a pin does not follow someone from
desktop to laptop, which is accepted.

`<main>` is already the horizontal scroll container, so the mechanism is
`position: sticky; left: 0` on the pinned lane — the smallest change that delivers
"always in", and one that touches layout rather than data.

## Evidence

- [[7]] — the original complaint and the transcript it came from.
- [[10]] — made every lane movable, which is what left this as the only remaining

## Residuals

- **Sticky and the drag transform collide.** `SortableLane` puts a `transform` on
  the same `<section>` during a drag, and a stuck element carrying a translate
  offsets from its stuck position rather than its natural one. The pinned lane also
  needs a `z-index` so others scroll under rather than over it; `paper-lane` sets
  none today.
- **Verify in a production build, not `next dev`.** This project has already been
  bitten by the CSS pipeline mangling positioning — Lightning CSS folded away
  `transform: none` where it sat beside `translate: none`, breaking the calendar
  float's fixed positioning in the served bundle while dev looked fine.
- **One pin or many.** Starting with one; more than one wants an order among them
  and eats the viewport on a narrow screen.
- **A pin on a lane that is deleted, or collapsed.** Both need an answer that is not
  a stuck empty column.
- **Whether Hap wanted a filter instead.** His literal words were *"look at all the
  things that need Hap"*, which an assignee filter answers more directly than any
  lane position. Assignee support shipped after [[7]] was written. Worth asking him
  before assuming the pin is what he was reaching for.
