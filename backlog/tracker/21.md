# #21 — Priority reordering from a filtered view can scramble the project-wide sequence

## Ask

Final review of the priorities planning screen (#9): `prioritizeCard`'s renormalisation writes ranks 1..n for exactly the ids the client sends. On the board-level page — or the project page with board chips active — the visible band is a subset of the project-wide band, so a drag there rewrites that subset while other boards' cards in the same band keep their old ranks. Result: cross-board rank collisions and ties resolved by lane order, degrading the "one global priority_rank sequence" the design claims.

## Status

**Backlog — not started.** Invisible today: the hosted project has one board, and cards never leave their band, so within-board order is always preserved. Becomes real the day a second board exists.

## Rationale

Two candidate fixes, either acceptable:

- Renormalise the full band server-side: fetch all band members project-wide, merge the visible order into the hidden cards' positions, write the whole band.
- Scope `priority_rank` per band per board and drop the "global sequence" claim from the design doc (`docs/plans/2026-09-06-priorities-planning-design.md`).

## Evidence

- Final whole-branch review of `feat/9-priorities` (merged as `14170e9`); the write path is `prioritizeCard` in `src/app/(app)/p/[project]/b/[board]/actions.ts`.
