# #11 — A card field you are typing in can be reset by someone else's change

## Ask

Found while building [[10]], not reported from a call.

A test that types into a card's date field went red once and passed on every rerun — the kind of result that normally gets written off as flake. It was traced instead, because the lane rework had just fixed a different bug with the same signature: a field that accepts a keystroke and silently keeps its old value.

The board is live. It subscribes to `cards` and `lanes` and refetches when anything changes. That is the feature. The defect is what the refetch does to a person who is part-way through typing.

## Status

**Backlog — not started.** Diagnosed during #10's final review; nothing built.

## Rationale

`useBoardRealtime` reacts to a change by refetching the board and calling `apply(snapshot)`, which replaces the whole `cards` and `lanes` arrays. Any card field is a controlled input reading from that array, so replacing it overwrites whatever the person has typed but not yet saved.

There is a guard, and it is the wrong shape. `apply` is held off while `busy` is true, where `busy = pending || laneBusy !== null`. `pending` is a `useTransition` flag: true while a save is **in flight**, false while someone is merely typing before they save. So the guard covers the window where a write is travelling and leaves open the window where the edit exists only on screen — which is the longer of the two and the only one a person is actually sitting in.

The trigger does not have to be another person. Any board activity that lands during the typing window will do it: a teammate moving a card, an import, a sync, or the app's own lane reorder before it settles.

This is pre-existing and predates #10 — that work changed neither `apply` nor the gate. It surfaced now only because #10's own defect had the same symptom and forced a close look at the area. #10 did narrow one contributing path by bringing lane reorders under the same busy gate as the other lane mutations.

## Evidence

- `src/components/board/use-board-realtime.ts` — the doorbell and refetch.
- `src/components/board/board-view.tsx` — `apply(snapshot)` replacing `cards`/`lanes` wholesale, and `busy: pending || laneBusy !== null`.
- `e2e/card-peek-fields.spec.ts:47` — went red once during #10's Task 8, passes 3/3 in isolation. That spec performs no drag, which is what ruled out #10's drag-render mechanism and pointed here.

## Residuals

- The fix wants a decision about what "dirty" means for a card. Tracking unsaved edits per field and holding `apply` off while any exist is one answer; merging a snapshot around the focused field is another; a conflict prompt is a third and the most work.
- Whatever is chosen has to keep the live board live. Holding refetches off for as long as a dialog is open would trade this bug for a stale one.
- Worth checking whether the same shape affects other controlled inputs fed from replaced state — the card dialog is the obvious one, but the board's filter and search inputs read from their own state and are probably safe.
